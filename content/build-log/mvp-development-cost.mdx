The fastest way to get a useful MVP estimate is to describe the first job a user must finish. Then say what the first release can leave out.

"How much does an MVP cost?" sounds like a request for a number. Usually it is a request for a boundary.

I can put a price on a defined build. I cannot give a useful one to "an app where users can do everything," because the word *everything* hides the work. Logins, payments, permissions, integrations, support, edge cases, speed, the thing that happens when a file is too large. Each one is a decision with a cost.

I build my own products, including [Pepys](https://pepys.co/) and [Whooshly](https://whooshly.co/). One turns recordings into useful text. The other connects links, QR codes, bio pages, landing pages and measurement. Both are good reminders that the first version has to complete a job. It does not have to contain the whole future roadmap.

## Which of these are you buying?

A prototype answers "Can people understand and react to this?" It can be clickable without a real backend. It can expose a bad workflow before you pay to automate it.

A working MVP answers "Can a real user finish the core job?" Data persists. The critical path works. There is enough design and reliability for a small group to use it and tell you what breaks.

A production release adds the things that make ongoing use and support possible: monitoring, recovery paths, billing or access controls where needed, support surfaces, and a way to change the product without breaking it.

These are not fixed industry price tiers. They are different promises. Two founders can say "MVP" and expect different ones.

## Make the first job painfully specific

Before asking for a quote, write one sentence:

> "A [specific user] can [complete one job] and know it worked because [observable result]."

For a transcription product, that might be: a person uploads a recording and gets text they can correct and export. For a campaign toolkit: a marketer creates a destination and can tell whether a link or QR code was used.

Those are illustrations of the kind of job, not a claim about how the current Pepys or Whooshly roadmap was ordered.

Now list the minimum pieces that make that sentence true. Then put every other feature into "later" until a real user or constraint pulls it forward. This is where cost gets clearer: fewer parallel user journeys, fewer integrations, fewer permission states and fewer exceptional paths.

## Four questions that move the estimate

Start with the user journeys. One role completing one task is different from buyers, admins and partners each needing their own experience.

Count the outside systems. An integration may need authentication, rate-limit handling, retries, field mapping and support when the other service changes.

Ask what can go wrong. A throwaway demo can tolerate failures that a paid product cannot. A production build needs to make bad inputs and interrupted work recoverable.

Name the person who makes the calls. Work slows when no one can decide what ships. A small build needs someone who can say yes, no and "not yet."

The cheapest first release is rarely the one with the least code. It is the one that creates a usable answer to the central question without taking on work the product has not earned.
